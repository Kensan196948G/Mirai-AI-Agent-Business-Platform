MIRAI AI AGENT BUSINESS PLATFORM — ELI5 SETUP GUIDE

desknet's NEO Workflow 設定手順書

NEO Workflowは、「会社として正式に承認する」ためのハンコのしくみです。この基盤では、案件が次の段階へ進んでよいかの関所（Gate 1〜5）を、ここで承認します。承認は必ず人間（3名）が行い、AIは承認しません。

ELI5（やさしい説明）実行者：DX推進部担当者 承認者：3名目安：2〜4日
これは何？ だれがやる？ じゅんび Gateのしくみ やり方 サンプル できた？ ちゅうい
1

これは何？

たとえると：NEO Workflowは「会社の正式なハンコ帳」。書類（申請）を出すと、決められた人が順番に見て、「よい」または「ダメ（差戻し）」を押します。その記録が全部残るので、「だれがいつ承認したか」をあとから確かめられます。
言葉説明
申請「この案件を次の段階に進めたいです」と出すお願い
承認決められた人（承認者）が「よい」と認めること
差戻し「ここが足りないので直して」と戻すこと。理由も記録される
Gate（ゲート）案件の関所。Gate 1〜5があり、それぞれ承認者（だれがハンコを押すか）が決まっている
承認フロー「申請 → だれが → だれが → 承認/差戻し」という順番の設計図
この基盤の鉄則：Slackなどでの「OK」の返事は正式な承認ではありません。正式な承認は必ずここ（NEO Workflow）の記録だけを正本とします。
2

だれがやるの？

人役割
DX推進部担当者承認フローの「しくみ（設計図）」を作る
社内経営企画担当者事業価値の承認（Gate 1・4・5等の最終承認）を担当する承認者になる
社内建設土木技術者/研究者業務の妥当性・技術受入（Gate 2・3・4等）を担当する承認者になる
IT/DX/AIシステム開発者システム面の承認者になる（ただし自分が作ったものの単独最終承認はしない＝SOD）
上位Gate Owner（最終ハンコ役）：高額案件やGate 5（本番リリース）の最終承認は「上位Gate Owner」が行います。3名体制では経営企画担当者が兼ねるか、役員を別途指定するかを事前に決めます（全体計画書 P-1・P-8）。未決定の場合は設定前に決定してください。
3

じゅんびするもの

  • NEO Workflow に3名のアカウントがあり、ログインできる
  • 「どのGateで、だれが、どんな順番で承認するか」の一覧（承認者マップ）を3名で決めておく
  • Gateごとの「承認条件」を決めておく（例：Gate 3ならKPI実績の報告が必須）
  • 申請書に添付する資料（企画書・要件定義書）のテンプレートが Notion に用意されている
  • 全体計画書（ai-dx-dev-saas-setup-guide.html）の 3.3 と第7章（P-1〜P-12）を確認済み
4

Gate 1〜5 のしくみ（承認者マップ）

Gate何の関所か承認者（3名体制での割り当て例）
Gate 1企画承認（この取組を進めてよいか）経営企画担当者（主）＋建設土木技術・研究者＋IT/DX/AI開発者
Gate 2開発承認（要件・仕様が固まったか）建設土木技術・研究者（業務受入）＋IT/DX/AI開発者　※作成者と承認者を分離
Gate 3MVP承認（試作品の効果が出たか）建設土木技術・研究者（技術受入）＋経営企画担当者（最終承認）
Gate 4本番移行承認（業務受入試験＝UATが通ったか）建設土木技術・研究者（受入判定）＋経営企画担当者（移行判定）
Gate 5Release承認（本番に出してよいか）上位Gate Owner（最終）＋IT/DX/AI開発者
3名体制の注意：承認フローを作るとき、「申請する人」と「承認する人」が同じ人にならないよう注意します。IT/DX/AI開発者が開発した案件の最終承認（Gate 5）は、別の人（経営企画担当者 or 役員）が行います。
5

やり方（手順）

1

Gate 1（企画承認）フローを作る

NEO Workflowで「企画承認申請」のフローを新規作成します。申請時に企画書（Notionのテンプレート）を添付できるようにし、承認者を上の表のとおり設定します。差戻し理由を必ず記録する設定にします。

DX推進部担当者（作成）
2

Gate 2〜5 のフローも同じようにつくる

Gate 2（開発承認）、Gate 3（MVP承認）、Gate 4（本番移行承認）、Gate 5（Release承認）の申請フローを、それぞれ承認者と添付資料を変えて作成します。申請の名前には案件IDを含められるようにします（例：DX-2026-0042 本番リリース申請）。

DX推進部担当者（作成）
3

承認者を3名で登録・確認する

各フローの承認者として3名（＋上位Gate Owner）を正しく割り当てます。このとき「承認者リスト」を3名全員で見て、間違いがないか確認します。

DX推進部担当者（登録）→ 3名（確認）
4

承認テンプレート（企画書・要件定義書）を添付できるようにする

Notionにある企画書・要件定義書のテンプレートを、各Gateの申請に添付できるよう連携・設定します。これで「申請のたびに書式をゼロから作る」手間がなくなります。

DX推進部担当者
5

テスト申請を1回流して通してみる

ためしに架空の案件（DX-2026-9999）でGate 1の申請を出し、承認者3名が順番に承認し、最後に「承認済み」になること、また差戻しもできることを確認します。テスト後は削除します。

DX推進部担当者 → 3名（実操作）
6

AppSuiteへの反映ルールを決める（手動 or 自動）

NEOで承認された結果を、AppSuiteの案件台帳の「Gate状態」にどう反映するか決めます。推奨：最初は手動転記（承認されたらDX推進部担当者がAppSuiteを更新）。自動連携（Webhook）が必要になったら、その時点で追加検討します（全体計画書 4.3）。

3名（決定）→ DX推進部担当者
だいたいの目安：フロー5本の作成で2〜3日。3名でのテスト承認・確認を入れると計4〜6日ほど見ておくと安心です。
6

サンプル（記入例）

ここでは、パイロット案件（例：現場写真・点検記録からの報告書自動作成 DX-2026-0042）でGate 1（企画承認）を申請するときの記入例を示します。

サンプル1：申請書の記入例（Gate 1 企画承認）

項目記入例
申請名DX-2026-0042 企画承認申請（現場写真・点検記録からの報告書自動作成）
申請者（例）現場監督（建設土木技術部）
添付資料企画書（Notionのテンプレートから作成）
承認依頼の内容本事案の企画内容を承認いただきたい。MVP範囲は「日常安全点検報告書」の自動作成とし、費用対効果・KPIは企画書のとおり。
承認経路（順番）建設土木技術者/研究者 → IT/DX/AIシステム開発者 → 経営企画担当者（最終）

サンプル2：差戻しの記入例

項目記入例
差戻し先申請者（現場監督）へ戻す
差戻し理由対象者（誰が使うか）の欄が未記入です。現場監督・施工管理者のどちらを対象にするか明確にしてください。あわせて、写真に写る人物・位置情報の取扱い方針を追記してください。

サンプル3：各Gateの申請名（案件IDを使う）

  • Gate 1：DX-2026-0042 企画承認申請
  • Gate 2：DX-2026-0042 要件・開発承認申請
  • Gate 3：DX-2026-0042 MVP承認申請
  • Gate 4：DX-2026-0042 本番移行承認申請（UAT結果を添付）
  • Gate 5：DX-2026-0042 本番リリース承認申請
7

できたか確かめる（完了チェック）

  • Gate 1〜5の承認フローが5本すべて作成された
  • 各フローの承認者が3名体制のルール（SOD）どおりに設定された
  • テスト申請で「申請 → 承認 → 承認済み」「差戻し」の両方が動くことを確認した
  • 申請に企画書・要件定義書（Notionテンプレート）を添付できる
  • 承認結果をAppSuiteのGate状態へ反映するルール（手動転記）が決まった
  • 承認履歴がNEOに残り、あとから「だれがいつ承認したか」を確認できる
8

ちゅういすること

  • AIは承認しない：承認は必ず人間（3名）が行います。AIの提案・下書きはあっても、最終のハンコは人が押します。
  • 申請者＝承認者を避ける：自分で申請したものを自分だけで最終承認するフローは作らないでください（SOD）。
  • 差戻し理由は必ず記録：「なぜダメだったか」を残すことで、あとで改善に使えます。
  • 承認と台帳のズレに注意：NEOの承認結果とAppSuiteのGate状態が食い違わないよう、反映ルール（手動転記）を守ります。
  • 上位Gate Ownerの未決定：Gate 5の最終承認者が未決定のまま設定を進めないでください。先に3名（＋役員）で決めます。
