AppSuite 設定手順書 公式マニュアル追記版

AppSuiteは、「どんな取組（案件）が今どこまで進んでいるか」を一覧で管理する台帳です。この手順書では、案件を正しく記録するための「下準備（マスタ登録）」と「台帳の項目決め」を、むずかしい言葉を使わずに説明します。

1

これは何？

たとえると：AppSuiteは「会社の取組の一覧表（ノート）」。どの取組に整理番号（案件ID）が付いていて、今どの段階（フェーズ）にいて、だれが責任者かが、ひと目で分かるようにする場所です。
役割説明
案件ID取組1つに付ける整理番号（例：DX-2026-0042）。資料・通知・台帳すべてをこの番号でつなぐ「共通の札」
マスタ「部署名」「社員名」「進み具合の名前」など、何度も使う基本データをあらかじめ登録しておく下準備
台帳アイデア → 企画候補 → 正式案件の3段階で案件を記録する表
Gate（ゲート）次の段階へ進んでよいかの「関所」。承認は必ず desknet's NEO Workflow で行い、その結果をここに記録する
この基盤での分担：AppSuite＝案件の状態を管理する場所（Process Master）。「承認する」作業そのものは desknet's NEO Workflow の担当です。AppSuiteには承認の「結果（Gate 1 承認済み など）」を反映します。
2

だれがやるの？

人役割
DX推進部担当者実際の設定作業を実施する（画面を開いて登録する人）
3名（経営企画／建設土木技術・研究／IT・DX・AI開発）台帳の項目・マスタの内容が正しいかを確認し、承認する
ポイント：「何を記録するか」は3名で決め、「画面にどう登録するか」はDX推進部担当者が行います。1人で勝手に決めず、必ず3名で確認してから進めます。
3

じゅんびするもの

  • 3名それぞれの AppSuite ログイン用アカウント（ID・パスワード）がある
  • マスタに登録する「部署名・3名の氏名」の一覧を用意する
  • 案件IDの付け方のルールを決めておく（例：年度＋連番 DX-YYYY-NNNN）
  • 「フェーズ（進み具合）」と「Gate（関所）」と「ステータス（状態）」の名前リストを用意する
  • この基盤の全体計画書（ai-dx-dev-saas-setup-guide.html）を開いておく
4

やり方（手順）

1

マスタの「中身」を3名で確認する

計画書の 3.1「共通マスタ・案件ID設計」の表を使って、以下が登録されている（または登録予定が正しい）かを確認します：
・案件ID採番ルール　・部署マスタ　・社員マスタ（3名＋承認者）　・Phase（フェーズ）マスタ　・Gate（ゲート）マスタ　・Status（状態）マスタ

3名（確認）
2

台帳の「項目」を3名で決める

案件を記録する表に、どの欄（項目）を置くかを計画書の 3.2「AppSuite（案件台帳）」を基に最終決定します。最低限の項目例：案件ID・案件名・提案者・責任者・フェーズ・Gate状態・期限・KPI・ROI。

3名（決定）→ DX推進部担当者（登録）
3

台帳のしくみを作る

AppSuite上に「アイデア台帳（Idea DBはNotion側）→ 企画候補台帳 → 案件台帳」の流れを作ります。企画候補に上がるのは、価値があると判断されたアイデアだけです。正式案件には案件IDを自動で付けられるようにします。

DX推進部担当者
4

KPI・ROIを記録する欄を作る

「この取組で、どれだけ時間が減ったか」「投資に対して効果があったか」を後から数字で確認できる欄を用意します。あとで効果測定（この基盤の目的のひとつ）に使います。

DX推進部担当者
5

ダッシュボード（あれば）を整える

経営企画担当者が「今どの案件がどこまで進んでいるか」を一覧で見られる画面を用意します（AppSuiteに機能があれば設定、なければ後日検討）。

DX推進部担当者
6

テスト案件で動きを確かめる

ためしに1件、架空の案件（例：DX-2026-9999 テスト）を登録し、「アイデア → 企画候補 → 案件ID発番」までがスムーズに動くか確認します。確認後、テスト案件は削除します。

DX推進部担当者 → 3名（確認）
だいたいの目安：設定作業は1〜2日。3名での確認・承認を入れると計3〜5日ほど見ておくと安心です。
4A

公式マニュアルに沿った「実画面」の作り方

公式手順 ここからは、desknet's NEO / AppSuite の公式オンラインマニュアル（製品 V9.6R1.0、マニュアル 9.6.1）で確認できる画面名・ボタン名に合わせて説明します。既存の設計方針は変えず、実際に管理画面で何を押すかを補います。
A1

AppSuiteで「案件台帳」アプリを新規作成する

AppSuite → [アプリケーションの作成] → [はじめから作成]

アプリケーション名を「AI/DX案件台帳」などにし、説明・ラベル・アイコンを必要に応じて設定して 作成 を押します。通常の案件台帳を作るだけなら、この「通常アプリケーション」で構いません。

作成には「アプリケーションの作成権限」が必要です。権限がない場合はボタン自体が表示されないことがあります。
A2

詳細画面と一覧画面を作る

対象アプリを開く → [アプリケーション設定] → 画面 → [画面デザイン]

画面の作成 から「詳細形式」「一覧形式」などを作成できます。詳細形式は案件の登録・変更・閲覧に、一覧形式は案件一覧の確認に使います。画面デザインでは、左側の部品を中央の画面へドラッグ＆ドロップして配置します。

この案件台帳で配置する部品の推奨対応

案件台帳項目AppSuite部品の例設定のポイント
案件ID文字（一行）自動採番を設定。例：任意文字列「DX-」＋採番日付（年）＋連番4桁。1アプリケーションにつき自動採番は1部品まで。
案件名文字（一行）必須項目に設定。
現状課題 / 期待効果文字（複数行）長文入力用。
提案者 / 責任者ユーザー選択ユーザーを直接選択できる形にする。
所属部署組織選択部署名の手入力を減らす。
Phase / Gate / Statusプルダウン選択肢をマスタ化した運用ルールに合わせる。
KPI / ROI数値 / 文字（一行）計算可能なものは数値、説明を伴うものは文字で持つ。
企画書・要件資料添付ファイル正式資料を添付する場合に使用。
A3

案件IDを自動採番する

画面デザイン → 文字（一行）部品 → 種類「自動採番」 → [自動採番設定]

自動採番では、任意文字列・採番日付・他の部品値を組み合わせ、連番の桁数（2〜9桁）やリセットタイミング（毎年・毎月・毎日・リセットなし）を設定できます。年度ごとに DX-2026-0001 のようにしたい場合は、年を含めて4桁連番＋毎年リセットを使う構成が分かりやすいです。

採番ルールは本番データ投入前に固定してください。途中変更すると「同じ見た目のID」や運用上の混乱を生みやすくなります。
A4

アクセス権を設定する

アプリケーション設定 → アクセス権 → [アプリケーション] / [データ] / [部品]

アプリケーション単位だけでなく、データ単位・部品単位でも参照／変更／削除の権限を設定できます。案件台帳では、一般利用者は参照中心、DX推進担当者は変更可、削除は管理者に限定する構成が安全です。

公式仕様では、データアクセス権は条件とユーザー／組織／ロールを組み合わせて設定できます。SODを実装する場合は「作成者」と「最終承認者」の権限を分けます。
A5

公開前テストを行う

テスト案件を1件登録し、①案件IDが一意に採番される、②一覧画面に必要項目が出る、③3名それぞれの権限で見える範囲・変更できる範囲が正しい、④削除権限が過剰でない、を確認します。

4B

AppSuite ＋ ワークフローの公式連携

推奨候補 AppSuiteには、ワークフローと直接つながる「申請書アプリケーション」があります。これを使うと、AppSuiteの詳細画面をワークフローの申請書として使い、その申請内容をAppSuite側でも管理できます。
AppSuiteで申請書アプリ作成→画面デザイン→ワークフロー申請経路設定→申請書を「完成」→申請テスト
B1

申請書アプリケーションを作成する

AppSuite → [アプリケーションの作成] → 「はじめから作成」右側の▼ → [申請書アプリケーション]

アプリケーション名を入力して 作成。この名前と同名のワークフロー申請書が自動的に作成されます。

公式仕様上、作成には「システム管理 ＞ 権限設定 ＞ 申請書アプリケーションの作成」が「許可する」であることに加え、システム管理者／ワークフローの「すべての申請」管理者／申請書・経路管理者のいずれかである必要があります。
B2

AppSuite側で申請画面をデザインする

案件ID、案件名、目的、期待効果、KPI、添付資料などを詳細画面に配置します。申請書アプリケーションでは、この詳細画面がワークフローの申請内容になります。

B3

ワークフロー側で申請経路を設定して「完成」にする

AppSuiteの誘導に従ってワークフロー側へ移動し、Gateに対応する承認者を設定します。申請書の状態を「完成」にすると利用可能になります。

B4

「申請の作成」からテストする

ワークフローの申請一覧へ戻り、申請の作成 から作成した申請書を選択し、入力→確認→申請を実行します。承認者側で承認・差戻しまで確認します。

この基盤への適用方針：初期導入で「AppSuite案件台帳」と「ワークフローGate申請」を別管理する方式は安全で分かりやすいです。一方、運用が安定したら、Gate申請を「申請書アプリケーション」に寄せることで二重入力を減らせます。公式標準機能なので、独自Webhookを先に作るより保守しやすい選択肢です。

6

できたか確かめる（完了チェック）

  • 3名がマスタの内容（部署・氏名・フェーズ・Gate・ステータス）を確認し「OK」を出した
  • 台帳の項目（案件ID・責任者・KPI等）が3名で決まり、AppSuiteに登録された
  • 案件IDの採番ルールが文書化され、テスト案件で一意（かぶらない）ことが確認できた
  • 企画候補台帳には「価値判断のあった案件」だけが登録されるしくみになっている
  • テスト案件の登録と削除が完了した
7

ちゅういすること

  • 1人で承認しない：「企画した人＝承認した人」にならないよう、作成者と承認者を分けます（SOD・職務分掌）。
  • 承認はAppSuiteだけでは完結しない：正式な承認は必ず desknet's NEO Workflow で行い、その結果をAppSuiteへ反映します。AppSuiteだけの記録は「状態の控え」です。
  • 案件IDは共通キー：同じ案件の資料（Notion・NEO・Slack・成果物）には必ず同じ案件IDを使います。
  • むやみに削除しない：台帳のデータは会社の記録です。削除や大きな変更は3名の確認を取ってから。
