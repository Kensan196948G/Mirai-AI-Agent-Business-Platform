Notion 設定手順書

Notionは、この基盤の「知識をためる図書館（Knowledge基盤）」です。アイデア・決定したこと・企画書・要件・教訓を、人間がレビューして「これで確定」となった情報だけを保存します。あとでAI（Lightblue）がここを参照して、次の相談に役立てます。

ELI5（やさしい説明）実行者：IT/DX/AIシステム開発者 利用：3名目安：2〜4日

1

これは何？

たとえると：Notionは「会社の図書館」。本（ページ）には「これは正式に決まった情報」というラベルが付いていて、だれでもあとから読めます。Slackでの雑談や途中のアイデアは「下書き」なので、ここには置きません。人間が「OK」を出した情報だけを棚に並べます。
置くもの説明（だれでも分かる言い方）
Idea DB（アイデア台帳）「こんなのあったら便利」を1件ずつ記録するカード箱。14個の項目（提案者・所属・課題・期待効果・MVPなど）を用意
Decision Log（決定記録）「いつ・だれが・なぜ・こう決めた」を残すノート
企画書テンプレート企画を出すときの「書き方の型紙」。何度も同じ書式を作らなくて済む
要件定義書テンプレート「システムに何をしてもらうか」を書く型紙。業務要件と非機能要件に分かれる
教訓台帳（Lessons Learned）案件が終わった後の「うまくいったこと・失敗したこと」の記録
Postmortem（ふりかえり）トラブルが起きたときの「原因・影響・対策」の記録用紙
ここが大事：Slackの会話やAIの出力は「そのまま」ここへ入れません。会話 → AIが整理 → 人間がチェック → Notionに保存、という順番を必ず守ります。これが「会社として信頼できる知識」だけをためる仕組みです。
2

だれがやるの？

人役割
IT/DX/AIシステム開発者Notionの「棚（データベース）と型紙（テンプレート）」を作る
3名（経営企画／建設土木技術・研究／IT・DX・AI開発）実際にページを書いたり、確定した情報を登録したりして利用する
将来：全社員のアイデア受付を始めるときは、ここを全社員が閲覧できる形に広げます（運用拡大時に設定）。
3

じゅんびするもの

  • Notionのアカウント（3名分）と、ワークスペースの作成
  • だれが「管理者（設定を変えられる人）」になるかを決める（推奨：IT/DX/AIシステム開発者）
  • 置く情報の種類（上の表の6つ）を3名で確認する
  • 全体計画書（ai-dx-dev-saas-setup-guide.html）の 3.4 を開いておく
4

つくるもの（構造）

Notionのワークスペースに、大きく分けて次の場所（ページ）を作ります：

  • トップページ（Home） — 基盤の案内と、各ページへの入り口
  • Knowledge基盤 — Idea DB・Decision Log・教訓台帳などの置き場
  • テンプレート置き場 — 企画書・要件定義書などの型紙（テンプレート）を保存
  • 案件ごとのProject Home — 案件ID（例：DX-2026-0042）ごとに作る、その案件の「ホームページ」。リンク集として使う（今後案件ができたら作る）
5

やり方（手順）

1

ワークスペースとトップページを作る

Notionに「Mirai AIエージェント事業推進基盤」のワークスペースを作り、トップページ（Home）に「何をする場所か」の案内と、下の各ページへのリンクを置きます。

IT/DX/AIシステム開発者
2

Idea DB（アイデア台帳）のデータベースを作る

「データベース」機能でIdea台帳を作り、列（プロパティ）を14個用意します：Idea ID・提案者・所属・原課題・壁打ち結果・目的・対象者・期待効果・MVP・概算工数・リスク・類似案件・関連Knowledge・ステータス。

IT/DX/AIシステム開発者
3

Decision Log・教訓台帳・Postmortemのデータベースを作る

「決定記録」「教訓台帳」「ふりかえり（Postmortem）」のデータベースを作ります。それぞれ、日付・案件ID・決定者（または担当）・内容・理由などの列を用意します。案件IDでほかの台帳とつながるようにします。

IT/DX/AIシステム開発者
4

企画書・要件定義書のテンプレート（型紙）を作る

「企画書」と「要件定義書」の型紙をテンプレートとして用意します。
・企画書：背景・目的・As-Is/To-Be・範囲・MVP・KPI・費用・ROI・情報管理・Security・リスク
・要件定義書：業務要件（機能・入力・処理・出力・承認・履歴）＋非機能要件（認証・RBAC・監査ログ・データ保管・AI送信最小化・性能）

IT/DX/AIシステム開発者（作成）→ 3名（内容確認）
5

アクセス権を設定する

現段階では3名＋案件関係者に閲覧・編集を制限します。社外秘・個人情報を守るため、ページやデータベースごとに「だれが見られるか」を設定します。全社員への公開は、運用拡大時にあらためて設定します。

IT/DX/AIシステム開発者
6

テストで1件登録して動きを確かめる

架空のアイデア（例：現場点検報告書の自動作成）をIdea DBに登録し、企画書テンプレートを開いて書けること、案件IDでほかの台帳とつながることを3名で確認します。

IT/DX/AIシステム開発者 → 3名（確認）
だいたいの目安：データベースとテンプレートの作成で2〜3日。3名での確認を入れると計4〜5日ほど見ておくと安心です。
公式

Notion公式マニュアルに沿った実画面操作

この章の目的：前章までの設計を、Notionの現行公式ヘルプに沿って実際の画面で設定できるようにします。画面名は2026年9月4日時点の公式ヘルプを基準にしています。
OFFICIAL STEP 1

Idea DBを新規作成する

  1. Notionで、Idea DBを置きたいページを開きます。
  2. 新しいページから作る場合は New page / 新規ページ を選びます。
  3. Get started with → ••• → Table を選びます。既存ページ内なら /database と入力してデータベースを作成する方法もあります。
  4. データベース名を Idea DB とします。
  5. 右側の ＋ / Add property から必要なプロパティを追加します。
  6. 既存プロパティの種類を変える場合は、プロパティ名 → Edit property → Change type を開きます。
公式：Notion Help - Create a database
OFFICIAL STEP 2

Idea DBの14項目をプロパティとして設定する

Notion公式では、Text / Number / Select / Status / Multi-select / Date / Relation / Person / ID などのプロパティ型が用意されています。本基盤では次の割り当てを推奨します。

本基盤の項目推奨プロパティ型設定メモ
Idea IDTextIDEA-2026-0001 のような社内書式を維持する場合。Notion標準の自動IDを使う場合は ID 型も選択可能。
提案者PersonNotionワークスペースのユーザーを割り当てる。
所属Select部署名を選択肢として登録。
原課題Text現状の困りごとを記録。
壁打ち結果Text整理済みの要点のみ。
目的Text達成したい状態。
対象者Multi-select / Text複数対象がある場合はMulti-selectが扱いやすい。
期待効果Text / Number時間削減など数値化する場合はNumberも利用可能。
MVPText最小検証範囲。
概算工数Number / Text日数で統一できる場合はNumber。
リスクText / Multi-select機密・個人情報・技術等の分類にMulti-selectも利用可能。
類似案件Relation案件DBを別に持つ場合、Relationで関連付ける。
関連KnowledgeRelationKnowledge DBとの関連付けに利用。
ステータスStatus例：Idea / Review / 企画候補 / 却下 / 完了。
本基盤での推奨：正式な案件ID・Idea IDの書式が既に決まっている場合は、Notion標準IDに無理に寄せず、Text型で社内共通キーを保持します。
公式：Notion Help - Database properties
OFFICIAL STEP 3

企画書・要件定義書をデータベーステンプレート化する

企画書や要件定義書を「文書DB」の1ページとして管理する場合、Notion公式のデータベーステンプレート機能を使うと、同じ章立てを毎回ワンクリックで作れます。

  1. テンプレートを置くデータベースを開きます。
  2. 右上の New の右側にあるドロップダウンを開きます。
  3. + New template を選択します。
  4. テンプレート名を 企画書テンプレート または 要件定義書テンプレート とします。
  5. ページ本文に、既存手順書で定義した「背景・目的・As-Is/To-Be・MVP・KPI…」等の見出しを登録します。
  6. 利用時は New のドロップダウンから対象テンプレートを選び、新しい文書ページを作成します。
公式：Notion Help - Database templates
OFFICIAL STEP 4

3名の権限を設定する

  1. 対象ページまたはデータベース右上の 共有 / Share を選択します。
  2. 招待する3名の名前またはメールアドレスを指定します。
  3. アクセスレベルを設定して招待します。
対象推奨権限理由
IT/DX/AIシステム開発者（管理担当）Full access / フルアクセス構造・共有・設定を管理するため。
経営企画担当者Can edit content / コンテンツ編集DBのページと値は編集できるが、プロパティやビュー構造を変更しにくくできる。
建設土木技術者・研究者Can edit content / コンテンツ編集同上。誤ってDB構造を変更するリスクを抑える。
外部公開禁止：本基盤のKnowledgeは社内用です。Anyone on the web with link 等の公開設定は原則使用しません。共有画面で意図せず一般公開されていないことを確認します。
公式：Notionヘルプ - コンテンツの共有 ／ Notion Help - Intro to databases
OFFICIAL STEP 5

データベース構造をロックする

  1. 対象データベースを開きます。
  2. データベース上部の設定メニューを開きます。
  3. Lock database を有効にします。
  4. 利用者がデータ入力はできる一方、ビューやプロパティを誤変更しにくいことを確認します。
補足：Can edit content 権限も、プロパティ・ビュー・フィルター・並べ替え等の構造変更を制限するのに有効です。ロックと権限を組み合わせると、運用事故をさらに減らせます。
公式：Notion Help - Customize your database settings ／ Notionヘルプ - データベース入門
OFFICIAL STEP 6

表示ビューを作り、テスト登録する

  1. データベース名の横にある ＋ から必要なビューを追加します。例：Table、Board。
  2. 設定メニューから Filter や Sort を指定します。
  3. 例として ステータス = 企画候補 のビューを作ります。
  4. New page からテストIdeaを1件登録します。
  5. 3名それぞれで、閲覧・編集できる範囲とDB構造が保護されていることを確認します。
完了条件：「登録できる」「必要な人だけ見られる」「DB構造を一般利用者が壊しにくい」「テンプレートから企画書を作れる」の4点が確認できればNotion初期設定は完了です。
公式：Notion Help - Create a database

項目記入例

サンプル3：企画書テンプレートの書き出し例

  • 背景：現場の点検記録は写真＋手書きメモが多く、報告書化に時間がかかっている
  • 目的：報告書作成の時間削減と記録品質の向上
  • As-Is：1件あたり約60分（写真整理・転記・帳票作成）
  • To-Be：1件あたり約20分（AIが所見案を作成し、人が確認）
  • KPI：作成時間／AI所見採用率／利用者満足度
  • MVP範囲：日常安全点検報告書の自動作成
  • 情報管理：人物・位置情報はマスキングしてAIへ入力
7

できたか確かめる（完了チェック）

  • Idea DB・Decision Log・教訓台帳・Postmortemのデータベースが作られた
  • 企画書・要件定義書のテンプレートが用意され、3名が内容を確認した
  • テスト案件で「アイデア登録 → 企画書作成」まで動いた
  • アクセス権が3名＋案件関係者に制限されている
  • 「確定した情報だけを保存する」運用ルールが3名に共有された（Slackの会話をそのまま入れない）
  • 案件ID（例：DX-2026-0042）で関連ページをたどれる
8

ちゅういすること

  • 生の会話をそのまま入れない：Slackの全ログやAIの出力を丸ごとNotionに保存するのは禁止。人間レビューを必ず通します。
  • AIは最終確認できない：「この情報を確定にする」のは必ず人間（3名）の判断です。
  • 案件IDでつなぐ：同じ案件のページには必ず案件ID（例：DX-2026-0042）を付けます。
  • アクセス権の確認：社外秘・個人情報を含むページは、対象者以外が見られない設定か定期的に確認します。
  • 成功も失敗も残す：教訓台帳には、うまくいったことだけでなく失敗・やめた理由も残します（次の企画に効く）。
