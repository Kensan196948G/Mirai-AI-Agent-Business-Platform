## 0. 経営・レビュー者向けサマリ（1枚で読む）

**何を作るか：** 全社員のアイデアを「アイデア → 企画 → 承認 → 開発 → 本番 → 効果測定 → ナレッジ」のルールで回し、**3名（経営企画／建設土木技術・研究／IT・DX・AI開発＝3 Authorityの担い手）が審査・承認・運用するための業務基盤（仕組みと設定）**。コードは書かず、会社で契約済みのSaaSを組み合わせて設定する。**Slack上での議論は3名のみで行う**（他の方は含めない）。

**今回必要なもの（大枠）：**

| # | 必要なもの | どこに作る | 状態 |
|---|---|---|---|
| 1 | 案件ID・部署・役割・Phase・Gate・Status のマスタ | AppSuite マスタDB | 構築済み（内容の突合確認が次工程） |
| 2 | アイデア台帳 → 企画候補台帳 → 案件台帳 の段階的台帳 | AppSuite | 一部構築済み（案件台帳の最終項目定義を確認） |
| 3 | Gate 1〜5 の承認フロー（申請・段階承認・差戻し・履歴） | **desknet's NEO Workflow**（正本）＋AppSuite（Gate状態） | 承認の実行場所は**決定済み（NEO Workflow）**。フロー定義が次工程 |
| 4 | 知識基盤（Idea / 決定事項 / 要件 / 教訓をためる場所） | **Notion（導入決定）** | **決定済み：Notion を導入しKnowledge基盤を構築**（第3.4節） |
| 5 | 日常議論・案件チャンネル／通知 | Slack（**参加3名のみ**）／**通知＝desknet's NEO** | **決定済み：Slack上の議論は3名のみ。通知はNEO** |
| 6 | AI窓口の壁打ちプロンプト・利用ルール・課題確認項目 | Lightblue | 契約済み（機能範囲はベンダー確認予定・設定が次工程） |
| 7 | 承認結果や状態変化の「通知・記録の連携」 | SaaS標準連携 or API/Webhook | **第4章で要否を判定** |

**自前アプリは不要か：** 基盤（案件管理フロー）については**不要と判定**（第4章）。「人間が承認・確認する」工程を挟む設計のため、リアルタイム双方向同期より「通知＋記録」で足りる。**ただし監視基盤は自前Web構築予定のため、監視基盤⇄各SaaSのデータ取得方法（API／Webhook）だけは別途検討が必要**（第4.4節）。

**Webhookの扱い（ご方針）：** GitHub等は**Webhookが必要なときのみ利用**。API接続としてWebhookが必要と判断した箇所は、第4章で都度指摘する（例：desknet's NEO API ⇔ Webhook ⇔ 他社製アプリ）。

**次にやること：** ① 本計画書のレビュー（3名）→ ② 第7章の追加決定ポイントP-1〜P-12を決定 → ③ Notion導入（Knowledge基盤のテンプレート作成）→ ④ 詳細設定手順書の作成 → ⑤ 1件のパイロット案件（例：現場写真・点検記録からの報告書自動作成）で通し検証 → ⑥ 運用開始。

## 2. 全体像（この基盤で回す流れ）

**基本的な流れは既存文書（Knowledge Feedback Loop）に準拠する。** 全社員のアイデア受付から始まり、Knowledgeとして次の相談に循環する。**Slack上での議論は3名のみで行う**（他の方は含めない）。

```text
全社員
  ↓
Lightblue（AI壁打ち）
  ↓
Slack Canvas → Notion（Idea / 確定Knowledge）※Slack上の議論は3名のみ
  ↓
AXWG → 3 Authority（経営企画 / 建設土木技術・研究 / IT・DX・AI開発）
  ↓
AppSuite（正式案件・Portfolio台帳）
  ↓
desknet's NEO Workflow（Gate審査・承認）… 承認は必ず人間
  ↓
Notion（要件・意思決定）
  ↓
Claude / Claude Code（要件・設計・レビュー・実装支援）
  ↓
GitHub（開発・テスト・Release）※Webhookが必要なときのみ利用
  ↓
MVP / Staging（UAT）
  ↓
Gate 5 → Production RC → Production Deploy
  ↓
監視基盤（DevSecOps）→ AppSuite / BI（KPI・ROI）
  ↓
Notion（Lessons Learned）
  ↓
Lightblue（次回相談の文脈）
  ↓
次のアイデア
```

| レイヤ | ツール（決定/案） | 役割 |
|---|---|---|
| AI Agent Layer | Lightblue | 全社員向けAI窓口（壁打ち・整理・検索・企画化支援） |
| Knowledge基盤 | **Notion（導入決定）** | Idea / 確定Knowledge / 要件・意思決定 / Lessons Learned。人間レビュー済みの確定知識を保存 |
| Process / Transaction | AppSuite | 案件ID・Phase・Gate・責任者・KPI・ROIの台帳（Process Master） |
| Governance（承認の正本） | **desknet's NEO Workflow**（決定済み） | 正式承認・差戻し・審査履歴 |
| Collaboration | Slack（**議論は3名のみ**）＋**desknet's NEO（通知）** | 日常議論・レビューは3名。状態変化の通知はNEO |
| 専門AI | Claude / Claude Code | 要件・設計・レビュー・実装支援 |
| Engineering | GitHub（Webhookが必要なときのみ） | 開発・テスト・Release（案件発生時） |
| 監視 | 自前Web構築予定（別途計画） | 稼働・AI利用量・KPI監視 |

> **重要な原則（既存文書から踏襲）：**
> - Slack等での「OK」は正式承認ではない。承認は必ず desknet's NEO Workflow に記録する。
> - AIは承認できない。AI出力は必ず人間レビューを経てNotionのKnowledge化する。
> - 案件ID（例：`DX-2026-0042`）を全成果物の共通キーにする。
> - **Slack上での議論は3名のみ**（社内経営企画担当者／社内建設土木技術者・研究者／IT/DX/AIシステム開発者。他の方は含めない）。

## 4. API / Webhook 連携の要否（自前アプリ不要の判定）

### 4.1 判定の考え方

本基盤の設計原則は **「承認・確定は必ず人間」**（Human-in-the-Loop）です。このため：

- **自動化してよい**：通知（誰が次に何をするか）、状態の転記・同期、定型変換、AIによる下書き生成
- **自動化しない**：Gate承認・差戻し判定・Knowledge化の最終確認（必ず人間）

### 4.2 連携パターン別の要否（基盤＝案件管理フロー）

| 連携したいこと | 手段 | 自前アプリ（受信サーバ）は必要か | 備考 |
|---|---|---|---|
| ① 案件状態変化（Gate承認等）を3名へ知らせる | **desknet's NEO の標準通知／メール通知** | **不要** | 通知先はNEOで決定済み |
| ② AppSuiteの案件情報をKnowledge（Notion）へ反映 | 人間が承認結果を転記 or AIが下書き→人間確認 | **不要** | 双方向リアルタイム同期は「やりたい場合」に追加判断 |
| ③ AI壁打ち結果をNotion Idea DB／案件台帳へ登録 | AIが下書き→人間レビュー→登録 | **不要** | 自動登録は任意（後述の「強化したい場合」） |
| ④ 承認フロー完了を通知・記録 | desknet's NEO Workflow の通知機能 | **不要** | 承認は必ずNEO内で完結し、結果をAppSuiteへ反映 |
| ⑤ LightblueがNotionのKnowledgeを参照（RAG） | Lightblue標準機能（プラン内） | **不要** | **Q6：ビジネスプランで可能かをベンダー確認** |
| ⑥ NEOの承認結果をAppSuiteのGate状態へ反映 | 手動転記（初期）→ 自動化したい場合はAPI/iPaaS（将来） | **不要（初期）** | 自動化は任意（下記4.3） |

**判定：基盤（案件管理フロー）の初期構築では、自前アプリ（外部受信サーバ・コード開発）は不要。**

### 4.3 「Webhookが必要なとき」と「自動化を強化したい場合」に追加するもの

**ご方針（Q4）：GitHub等はWebhookが必要なときのみ利用。API接続としてWebhookが必要と判断した箇所は都度指摘する。**

本計画書で現時点に判断できる範囲では、**初期構築で必須のWebhookはない**。ただし、以下の「やりたいこと」が発生した時点でWebhook／API連携が必要になる（その時点で都度、接続構成を指摘する）。

| やりたいこと | Webhook/APIが必要になる接続（例） | 追加するもの |
|---|---|---|
| NEO承認 → AppSuite Gate状態を自動更新 → 3名へ通知 | desknet's NEO API ⇔ Webhook ⇔ AppSuite／通知 | ノーコード連携基盤（iPaaS）or Webhook受信サーバ |
| NEO／AppSuite の状態変化をNotionへ自動反映 | desknet's NEO API ⇔ Webhook ⇔ Notion（またはAppSuite API ⇔ Webhook ⇔ Notion） | iPaaS or Webhook受信サーバ |
| AppSuite ⇄ Knowledge（Notion） の双方向リアルタイム同期 | AppSuite API ⇔ Webhook ⇔ Notion API | API連携・Webhookの設計 |
| 監視基盤（自前Web）が各SaaSの状態を受け取る | 各SaaS API ⇔ Webhook ⇔ 監視基盤 | 監視基盤側のWebhook受信機能（別途計画・4.4） |

> **推奨：** 最初は「NEO通知＋人間による確認・転記」で回し、運用で「ここは自動化したい」が明確になった箇所だけ、上記の接続を追加する。Webhookが必要になった時点で、接続元（desknet's NEO API等）と接続先（AppSuite／Notion／監視基盤）の対応表とともに具体案を提示する。上記の接続を実装する際の受け皿として、`AIDX開発基盤インフラ・ネットワーク構成設計書.html`にVLAN170（INTEGRATION、Integration Hub、必要時追加）がPhase 3として設計済み。

### 4.4 監視基盤（自前Web構築予定）との関係 — 要確認

監視基盤は **「自前でWebベース構築予定」** のため、基盤自体の自前アプリ不要の判定とは別に、以下を監視基盤計画側で検討する（本計画書のスコープ外・別途計画）。

| 論点 | 内容 |
|---|---|
| 監視対象 | 案件フローの各工程・AI利用量（Lightblue）・エラー等。既存文書の「監視項目」を参照 |
| データの取得方法 | 各SaaSの管理画面を人が見る／レポート出力／**API連携／Webhook受信** のいずれで監視基盤へデータを渡すか。**SaaS側にWebhook送信機能やAPIがあるかが分岐点** |
| 監視基盤⇄NEO | 通知はNEO経由にするか、監視基盤独自の通知にするか |
| 本計画との関係 | 監視基盤は本計画（案件管理フロー）とは別計画として切り分け、段階F（通し検証）の後に着手を推奨 |

> **補足：** 監視基盤を自前Webで作る場合、そこで初めて「API・Webhook・サーバ」が必要になる。必要ならこの基盤の「将来オプション（4.3）」と技術構成を共有してよい。

| P-12 | 文書・設定のバックアップと引継ぎ | 本計画書を含む設定資料・テンプレートの保存場所と、担当者不在時の引継ぎ方法。**推奨：社内の共有フォルダ等に設定資料を集約し、バックアップ頻度を決める** | |

## 付録A：用語集（非エンジニア向け）

| 用語 | 説明 |
|---|---|
| 案件ID | 1つの取組（例：現場点検報告書の自動作成）に振る整理番号。`DX-2026-0042` のように年度＋連番で、台帳・資料・通知すべてをこの番号で紐づける |
| Phase | 案件の進み具合（段階）。アイデア → 企画 → 要件 → MVP → 本番準備 → 本番 → 運用 |
| Gate（ゲート） | 次の段階へ進んでよいかの「関所」。Gate 1〜5の承認を経て進む。承認は必ず人（desknet's NEO Workflow）が行う |
| 正本 | 「正式な記録はここ」と決めた場所。二重管理を防ぐためのルール（承認の正本＝NEO Workflow、案件台帳の正本＝AppSuite） |
| Workflow（ワークフロー） | 申請 → 承認 → 差戻し の流れをシステム上で管理する機能（desknet's NEO Workflow） |
| MVP | まず一番小さく・速く作って試す範囲（Minimum Viable Product）。効果を確かめてから広げる |
| SOD（職務分掌） | 「企画する人と承認する人を分ける」等、1人で全てを決められないようにする仕組み |
| RAG | AIが社内の知識を検索して、その内容に基づいて回答する仕組み |
| KPI / ROI | KPI＝効果を測る数値（例：作成時間）。ROI＝投資に対して得られた効果 |
| SSO | 1つのID・パスワードで複数のシステムにログインできる仕組み。将来導入予定 |
