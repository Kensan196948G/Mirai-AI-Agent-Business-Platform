全体レビュー観点
  • 各ツールの責務が重複していない
  • 正本となるシステムが情報種別ごとに明確
  • 案件IDでシステム横断トレースが可能
  • AIが直接「会社としての確定情報」を上書きしない
  • Human Reviewを通した情報のみKnowledgeとして再利用する
  • 権限・監査ログ・情報管理方針が定義されている

06

設計原則

ツール原則
1. Slack「話す場所」 — 自由な相談・議論・レビュー・通知を行う。
2. Lightblue「考えるAI」 — 壁打ち・整理・検索・企画化を支援する。
3. Notion「覚える場所」 — 人間レビュー済みの確定Knowledgeを保存する。
4. AppSuite「案件を管理する場所」 — Phase・Gate・責任者・KPI・ROIを管理する。
5. desknet's NEO Workflow「会社として承認する場所」 — 申請・承認・差戻し・決裁を管理する。
6. Claude「専門的に考えるAI」 — 要件・設計・レビュー・開発を支援する。
7. GitHub「作る場所」 — Issue・Code・PR・Test・Releaseを管理する。
8. 監視ツール「見守る仕組み」 — 性能・可用性・エラー・Security Event・AI Cost等を継続監視する。
最重要原則 
Conversation
 ↓
AI整理
 ↓
Human Review
 ↓
Notion Knowledge
Slack上の古い発言、誤解、途中案、雑談をAIが同等のKnowledgeとして扱わないようにする。
会社として信頼できるKnowledgeのみをNotionへ蓄積する。
そのKnowledgeをLightblue、Claude、将来のAI Agentが再利用することで、開発プロセス自体が継続的に賢くなる循環型AX基盤を形成する。
07

全体レビュー用チェックリスト

Governance

  • Phaseごとの責任者が明確
  • Gateごとの承認者が明確
  • SOD（職務分掌）が定義されている
  • AI単独で正式承認される工程がない
  • 差戻し・再承認ルールが定義されている

Knowledge

  • NotionをKnowledge / Contextの中心としている
  • Raw Conversationをそのまま確定Knowledgeにしない
  • Decision Logを残す
  • Lessons Learnedを残す
  • RAG対象Knowledgeを人間が確認する

Process

  • AppSuiteをProcess Masterとしている
  • 案件IDが全システム共通キーになっている
  • Phase / Gate / Statusを追跡できる
  • KPI / ROIを案件単位で管理できる

Engineering

  • GitHubをEngineering SoRとしている
  • Issue / PR / Test / Releaseが追跡可能
  • CI/CDが定義されている
  • Security Scanが含まれる
  • StagingとProductionが分離されている
  • Rollbackが設計されている

Security

  • SSO / 認証方式が定義されている
  • RBACが定義されている
  • 監査ログが取得できる
  • AIへの送信データ最小化が設計されている
  • 個人情報・機密情報の取り扱いが明確
  • Stagingで本番データを利用しない

Operations / Monitoring

  • 監視ツールの役割が定義されている
  • 監視対象が定義されている
  • Alert条件が定義されている
  • Incident対応フローが定義されている
  • Postmortemを実施できる
  • AI Costを把握できる

Business Value

  • 導入前Baselineがある
  • KPIを継続測定できる
  • ROIを算出できる
  • 利用者Feedbackを収集できる
  • 効果測定結果を次の改善へ利用できる
