# 外部連携 仕様案（D-20〜D-23）と Approval PR に向けた確認事項

作成日: 2026-09-09 ／ 状態: **仕様確認待ち（実装は接続基盤のみ）**

本書は、Mirai AgentOS（業務Agent Runtime）と既存 SaaS を接続するために「何を・どの権限で・どう拘束して」行うかの案と、実装前に確認が必要な事項をまとめる。外部への接続・書き込み・production secret の追加はすべて **Approval PR（Y/N 承認）対象** であり、本書の承認だけでは実行しない。

## 0. すでに実装済みの基盤（PR: 業務ワークフロー統合の基盤）

| 基盤 | 内容 |
|---|---|
| 接続状態の実判定 | Integrations 画面は環境変数の有無と読み取り専用の疎通確認で状態を決める。手動で「接続済み」にする手段は無い（未接続を成功表示しない） |
| 正式承認参照の枠 | `approval_requests.external_ref`（desknet's NEO の承認番号）は **常に「未検証」** で保存し、承認の成立には使わない。「検証済み」にできるのは NEO 連携で検証できた場合のみ（現在は blocked） |
| 承認拘束 | Skill 契約の `approval_gate` で Step 実行前にアプリ内承認を要求できる（C-13）。外部書き込み（A2）はこれを必須にする |
| 冪等台帳 | `effect_ledger`（idempotency_key / status: pending → sent → confirmed）。外部書き込みは必ずここを通し、二重送信と「送ったふり」を防ぐ |
| AI相談 → 業務Agent | 相談の構造化結果から `technology-selection` の相談欄へ転記（D-24。人が確認してから開始） |

## 1. D-20 desknet's NEO Workflow（正式承認 SoR）— 自律度 A1（読み取りのみ）

- 目的: Gate 承認（R3 以上、本番リリース等）の **検証済み参照**。承認番号・状態・承認者・日時を NEO から取得し、アプリ内承認と突き合わせる
- やらないこと: NEO 側の承認の作成・判定・取消（人が NEO で行う）。手入力の承認番号を承認の成立に使うこと
- 確認事項（**回答が必要**）
  1. NEO Workflow に外部参照 API（Web API / CSV エクスポート / 通知メール等）があるか。契約プラン上の利用可否
  2. 認証方式（API トークン / IP 制限 / 専用アカウント）と、読み取り専用の権限が発行できるか
  3. 対象ワークフロー（申請書テンプレート）の ID と、承認番号のフォーマット
- 実装案: `neo` コネクタ `getApproval(externalRef)` → `{ status, decided_by, decided_at, subject }` を返し、一致すれば `external_ref_status='verified'`。不一致・取得不能は `unverified` のまま。検証結果は監査ログへ
- Approval PR: `NEO_BASE_URL` / `NEO_API_TOKEN`（production secret）、Cloudflare / ネットワークの egress 許可

## 2. D-21 AppSuite（案件・Phase・KPI SoR）— 自律度 A1

- 目的: 共通案件 ID（`DX-YYYY-NNNN`）で AppSuite の案件と本アプリの Run / 成果物を対応付ける（`agent_runs.project_id` → `projects.project_code` が既に存在）
- 確認事項
  1. AppSuite の REST API（アプリ ID・フィールド ID）と API トークンの発行可否
  2. 案件アプリのどのフィールドが「案件 ID」「Phase」「KPI」か
  3. 書き込み（状態控えの更新）を行うか。行う場合は A2 として承認拘束
- 実装案: `appsuite` コネクタ `getProject(code)` で参照し、案件画面に「AppSuite 側の Phase」を表示。書き込みは第 2 段階
- Approval PR: `APPSUITE_BASE_URL` / `APPSUITE_API_TOKEN` / `APPSUITE_PROJECT_APP_ID`

## 3. D-22 Notion（確定 Knowledge）— 自律度 A2（承認拘束の書き込み）

- 目的: `promoted` になった Knowledge を Notion の Knowledge DB にページとして作成（正本は Notion）。読み取りは「レビュー済み Knowledge のスナップショット」に限定
- 段階: (1) 読み取り専用（DB 一覧・ページ参照）→ (2) ページ作成（`approval_gate` 必須、`effect_ledger` で冪等）
- 確認事項
  1. Notion Integration（内部インテグレーション）の作成と、対象 DB の共有設定
  2. Knowledge DB のプロパティ（タイトル / 種別 / 出典 / 有効期限 / 版）の対応表
  3. 書き込み時の命名規則・重複時の扱い（既存ページの更新 or 新版作成）
- Approval PR: `NOTION_API_TOKEN` / `NOTION_KNOWLEDGE_DATABASE_ID`、書き込みを有効化する Skill 改訂（`approval_gate: { required: true, role: Knowledge Curator }`）

## 4. D-23 Slack（通知）— 自律度 A2

- 目的: Run 完了・レビュー依頼・失敗の通知。Slack の「OK」を正式承認に変換しない。生ログを Knowledge 化しない
- 確認事項
  1. Bot トークンのスコープ（`chat:write` のみ）と通知先チャンネル
  2. 通知に含めてよい情報（Run コード・Agent 名・成果物コード・リンクのみ。相談本文や出典本文は含めない）
- 実装案: `notifier` が `effect_ledger` に `pending` を記録 → 送信 → `sent`。失敗は `failed` として再送は人が判断。送信は `approval_gate` ではなく **通知ポリシー（許可リストのイベント種別のみ）** で制御し、内容に秘密・個人情報を含めない検査（prompt-guard の秘密検出）を通す
- Approval PR: `SLACK_BOT_TOKEN` / `SLACK_NOTIFY_CHANNEL`

## 5. 共通の安全条件

- 資格情報は環境変数（Secrets）からのみ読み、値をログ・DB・画面・PR に出さない。追加・変更・rotation は Approval PR
- 開発用 Mock は本番で受理しない（`NODE_ENV=production` では無効）
- 外部書き込みは `approval_gate` + `effect_ledger` を必ず通し、外部側の確認（ページ ID / ts）を `confirmed` に記録する
- 連携先の障害時は Run を `failed` / `paused` で明示し、成功を装わない
