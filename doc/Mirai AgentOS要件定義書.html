MIRAI AGENTOS / REQUIREMENTS DEFINITION

Mirai AgentOS
要件定義書

会社保有ITシステムから完全独立し、自前Notion・Slack・Gmail・GitHub・ローカルPostgreSQL・AIサービスを統合して、AI相談、案件化、承認、開発、テスト、本番、運用、効果測定、ナレッジ化を一貫管理するAgentic Operating Systemの要件を定義する。

Version 0.1Local PostgreSQLHuman-in-the-LoopKnowledge DrivenCompany-IT Independent
目的範囲ロール全体像機能要件非機能SecuritySoRAI運用受入
01

目的・背景

目的：AI/DX案件のライフサイクルを、相談・企画・承認・開発・運用・Knowledge循環まで一つの統制基盤でつなぎ、「AIとの個別対話」で終わらず、再現可能・監査可能・再利用可能な組織的プロセスへ変換する。

Process統合

Project / Phase / Gate / Task / Approval / KPIをAgentOS自身で管理。

AI統制

複数Agent・複数モデル・ToolsをPolicyとApprovalの下で実行。

Knowledge循環

結果・判断・失敗・教訓を人間レビュー後にNotionへ戻す。

02

適用範囲・前提・対象外

2.1 前提

ID前提
ASM-001desknet's NEO、AppSuite、Workflow、M365、AD、SharePoint等の会社保有ITシステム／ITサービスを利用しない。
ASM-002Knowledge基盤として自前Notionを利用する。
ASM-003Collaborationとして自前Slackを利用する。
ASM-004外部メール受付・自動返信・通知として自前Gmailを利用する。
ASM-005Engineering SoRとしてGitHub Private Repositoryを利用する。
ASM-006Process SoRはローカルPostgreSQLとし、Neonは利用しない。
ASM-007実行基盤はDockerを基本とし、初期段階ではKubernetesを必須としない。

2.2 対象範囲

  • AI相談受付、Idea構造化、正式案件化
  • Project / Phase / Gate / Task / KPI
  • Approval / Policy / Audit Trail
  • Agent Orchestration / Model Routing / Skills / Tools
  • Notion / Slack / Gmail / GitHub連携
  • MVP、Test、Staging、UAT、Production、DevOps、効果測定
  • Knowledge CuratorによるKnowledge候補抽出・昇格
  • 監視、Logging、Backup、Restore、監査

2.3 初期対象外

  • 会社基幹システムとの直接連携
  • 会社AD / Entra ID / M365 SSO
  • Kubernetesによる大規模クラスタ
  • 完全自律Production Deploy / IAM / Secret変更
  • AI単独による建設土木の重要技術判断

05

機能要件

5.1 Request / Project / Workflow

ID要件優先度
FR-001WebUIまたはSlackから自然言語でAI相談・案件依頼を登録できる。MUST
FR-002RequestをIntent分類し、対象Project、Request Type、Risk候補を特定できる。MUST
FR-003Ideaから正式Projectへ昇格し、一意なProject IDを発番できる。MUST
FR-004ProjectごとにPhase、Gate、Owner、Status、期限、KPIを管理できる。MUST
FR-005GoalをTask/SubTaskへ分解し、依存関係・完了条件を保持できる。MUST
FR-006Workflow State Transitionを定義し、不正遷移を拒否できる。MUST
FR-007TaskのRetry、Timeout、Cancel、Resumeを管理できる。SHOULD

5.2 Approval / Policy / Audit

ID要件優先度
FR-101ActionごとにRisk Levelを判定できる。MUST
FR-102Risk、Role、Action Typeに基づきPermit / Deny / Approval Requiredを判定できる。MUST
FR-103Approval Requestに複数Stepを定義し、承認・差戻し・却下を記録できる。MUST
FR-104Evidence、理由、対象Version、実行対象を保存できる。MUST
FR-105Audit Eventは追記型とし、履歴を上書きしない。MUST
FR-106R4以上のProduction / IAM / Secret / Destructive ActionはHuman Approvalなしに実行できない。MUST

5.3 Agent / AI / Knowledge

ID要件優先度
FR-201Research / Architect / Developer / Reviewer / Operations / Knowledge Curator等のAgentを登録・選択できる。MUST
FR-202Task特性に応じClaude / Codex / DeepSeekをModel Routerで選択できる。MUST
FR-203AgentにSkillとToolを動的に割り当てられる。MUST
FR-204Agent Run、Model Run、Tool Call、Error、Token、Cost、Latencyを記録できる。MUST
FR-205実装モデルと最終Reviewモデルを分離できる。MUST
FR-301NotionからProject / ADR / Research / Playbook / Standards等を必要範囲だけ取得できる。MUST
FR-302実行結果からKnowledge Candidateを生成し、人間レビュー後にNotionへ反映できる。MUST
FR-303Slack Raw ConversationをそのままKnowledge化しない。MUST
FR-304GitHub Repository / Issue / PR / Test / ReleaseをProjectへ紐付けられる。MUST
FR-305Gmail受信を分類し、Projectへ紐付け、Policyに応じ自動返信またはHuman Reviewへ送れる。SHOULD

非機能要件

IDカテゴリ要件
NFR-001AvailabilityMVPは単一ホストを許容するが、停止・再起動・復旧手順を文書化する。
NFR-002ScalabilityWorkerを水平追加できる疎結合構成とする。
NFR-003MaintainabilityKernel / Agents / Skills / Integrations / Policy / Dataをモジュール分離する。
NFR-004PortabilityDocker Composeで再現可能な環境を構築する。
NFR-005ObservabilityMetrics / Logs / Agent Runs / AI Usage / Approval / Security Eventを観測する。
NFR-006RecoverabilityPostgreSQL Backup / WAL / Restore Testを定期実施する。
NFR-007TraceabilityRequest → Plan → Task → Agent Run → Artifact → Approval → Release → Knowledgeを追跡可能にする。
07

Security / Identity要件

  • SEC-001: authentikによる独立認証・RBAC。
  • SEC-002: 管理UI、PostgreSQL、Grafana、RunnerはTailscale等Private Networkを基本とする。
  • SEC-003: SecretをGitHub / Notion / Slack / Logへ平文保存しない。
  • SEC-004: Tool実行前にPolicy Checkを必須化。
  • SEC-005: Audit Eventは改ざん検知可能に保持。
  • SEC-006: 契約・金額・Security・機密・承認事項のGmail自動返信を禁止。
  • SEC-007: Agent Sandboxと管理Planeを分離。

09

AI Governance要件

モデル分離

実装・Review・承認を単一モデルに集中させない。

説明可能性

Plan、Knowledge、Tool Call、判断理由、結果を追跡。

Self-Improvement制御

Candidate → Test → Eval → Approval → Promotion。

10

運用・監視・Backup要件

  • Grafana / Prometheus / Loki / AlloyでPlatform・Agent・AI・Securityを監視。
  • PostgreSQLは定期pg_dump、WAL Archive、別物理ディスク、Restore Test。
  • Agent Failure Rate、Retry、Duration、Token、Cost、Model Errorを可視化。
  • 重大Incident後はPostmortemをKnowledge候補化。
11

MVP受入条件

最重要：「1つのIdea → Project化 → Approval → GitHub実装 → Test → Production相当 → KPI記録 → Knowledge化」を、会社ITを一切利用せず一周できること。
IDAcceptance Criterion
AC-001Docker ComposeでAgentOS一式を再現起動できる。
AC-002Project / Phase / Gate / Task / ApprovalをPostgreSQLのみで管理できる。
AC-003R4以上ActionがApprovalなしで実行されない。
AC-004Notion Knowledgeを参照してAgent Planを生成できる。
AC-005GitHub Issue / PR / Test / Releaseへ連携できる。
AC-006複数モデルをTask単位で使い分けられる。
AC-007実装AgentとReview Agentを分離できる。
AC-008Execution ResultからKnowledge Candidateを生成しNotionへ反映できる。
AC-009Metrics / Logs / Agent Runs / Approval Eventsを確認できる。
AC-010PostgreSQL BackupからRestore Testを実施できる。
