MIRAI AGENTOS / ENGINEERING DESIGN OVERVIEW

Mirai AgentOS
エンジニア向け技術設計概要

会社保有ITシステムから完全独立し、自前Notion・Slack・Gmail・GitHub・ローカルPostgreSQL・AIサービスを統合する Agentic Operating System。案件・承認・AI実行状態・監査をAgentOS自身で保持し、KnowledgeはNotion、 Engineering履歴はGitHub、Process状態はPostgreSQLに分離する。

01

設計原則

Boundary

会社ITと完全分離

desknet's NEO、AppSuite、Workflow、M365、AD、SharePoint等には依存しない。

System of Record

正本を分離

Knowledge / Process / Engineering / Observabilityを別々のSoRへ分離する。

Control Plane

AgentOSがProcess Master

案件、Phase、Gate、Task、Approval、Audit、Agent Runtime ControlをAgentOS自身で管理。

Human-in-the-Loop

高リスク操作は人間承認

Production、IAM、Secret、破壊的操作はPolicy EngineとApproval Gateを通す。

Knowledge

Slack ≠ Knowledge

会話をそのままNotionへ保存せず、AI整理・人間レビュー後に確定知識化。

Runtime

AIモデルとAgentを分離

Agentは責務、LLMは思考エンジン。Model Routerで実行時に選択する。

Notion = 何を知っているか ／ PostgreSQL = 今何をしているか ／ GitHub = 何を作ったか

03

AgentOS Kernelの責務

Component責務主な入出力
Intent Routerユーザー依頼を分類し、対象Project・Request Type・Risk候補を特定Request → Intent Context
PlannerGoalをTask/SubTaskへ分解し、依存関係・成果物・完了条件を定義Goal → Execution Plan
Agent OrchestratorAgent選択、Task割当、結果統合、再試行、委譲Plan → Agent Runs
Workflow EnginePhase/Gate/State Transitionを管理Project State → Next State
Task Scheduler非同期Task、定期Task、待機中Taskを実行Task Queue → Worker
Policy Engine権限、Risk、実行可否、Approval要否を判定Action Context → Permit/Deny/Approve
Approval Gate人間承認・差戻し・却下、Evidenceの記録Approval Request → Decision
Model RouterTask特性に応じてClaude/Codex/DeepSeekを選択Task Profile → Model
Skill RegistrySkillの発見、Version、権限、適用条件を管理Agent Context → Skills
Knowledge Curator実行結果からKnowledge候補を抽出しNotionへ昇格Run Result → Knowledge Candidate

Workflow / Approval / Audit

Approval Data Model

approval_requests を起点に、approval_steps、approval_actions、 approval_evidence、approval_policies を分離する。

Append-only Audit

承認履歴は上書き更新せず、Requested / Approved / Rejected / Returned等を追記型イベントとして保存する。

REQ-000042
type: ProductionRelease
target: DX-2026-0042 v1.4.0
requested_by: DeveloperAgent
risk: R4

Required Steps
  1. Technical Review   -> Approved
  2. Security Review    -> Approved
  3. Owner Approval     -> Pending

Audit Events
  19:10 Requested
  19:14 Technical Approved
  19:27 Security Approved
  19:31 Owner Approved
Risk例推奨制御
R0Read-only / Public Research自動
R1Knowledge候補作成自動＋Audit
R2Branch / PR作成自動＋Review
R3Merge条件付きApproval
R4Production DeployHuman Approval必須
R5Secret / IAM / PrivilegeHuman Approval必須
R6Delete / Destructive Operation強いApproval + Rollback確認

Agent != Model

Agent:
  Research / Architect / Developer / Reviewer / Operations / Knowledge Curator

Model:
  DeepSeek / Claude / Codex
Service主用途位置づけ
DeepSeek大量処理、分類、調査、反復General / Cost-efficient Model
DeepSeek HarnessAgent Runtime / Execution LoopRuntime
Claude高度分析、設計、文書化Expert Reasoning
Claude CodeRepository単位の開発Coding Runtime
Codex開発、検証、独立レビューCoding / Review
モデル分離原則：実装モデルと最終レビュー/検証モデルを分離し、 同一モデルが「実装 → 自己評価 → 承認」まで自己完結しないようにする。

Integrations

Slack

Collaboration Gateway

相談、レビュー、通知、Agent呼び出し。Raw ConversationはKnowledgeに直接昇格しない。

Gmail

Mail Gateway

外部メール受付・自動返信。契約・金額・Security・承認・機密はHuman Reviewへ。

GitHub

Engineering Adapter

Repo、Issue、PR、Actions、Release。self-hosted runnerとの連携を前提にできる。

Notion

Knowledge Adapter

AI-CTO Knowledge BaseをLong-term Memoryとして参照・更新。

authentik

Identity / RBAC

会社AD/Entra IDを使わず、AgentOSの独立Identity Providerとする。

Tailscale

Private Network

Admin UI、PostgreSQL、Grafana、RunnerをInternetへ直接公開しない。

n8nは任意。Gmail/Slack/Webhook等のIntegration Automationに限定し、 AgentOS内部のPlan / Task / Approval / Execution / Retry / RollbackはAgentOS自身で保持する。

実装優先順位

Priority実装対象完了条件
P0Repo / Docker / PostgreSQL / Migration基盤ローカルで一括起動・停止可能
P1Project / Phase / Gate / Task Model案件状態がPostgreSQLだけで管理可能
P2Approval / Policy / Audit高リスクActionが承認なしに実行されない
P3Notion / GitHub AdapterKnowledgeとEngineering SoR連携が成立
P4Agent Orchestrator / Model Router1 Goalを複数Agent/Modelで処理可能
P5Slack / Gmail Gateway外部入口からAgentOS Requestを生成可能
P6ObservabilityAgent Run / Error / Latency / Costを可視化
P7Knowledge CuratorExecution ResultからNotion Knowledge候補を作成可能
MVPの成功条件： 「1つのIdea → Project化 → Approval → GitHub実装 → Test → Production相当 → KPI記録 → Knowledge化」 を、会社ITを一切使わず一周できること。
